================ GRAND STORE ACCOUNTING STRUCTURE.docx ================

The developer should build the accounting structure from the beginning, rather than trying to identify payments from bank statements later.   This should be smooth and streamlined 1. THE MOST IMPORTANT RULE Every financial transaction on Grand Store should receive  one permanent unique Transaction ID . For example: GS-26-AUC-000184 That tells you: GS  = Grand Store 26  = 2026 AUC  = Auction 000184  = unique transaction But I would go one step further. The customer should see a  human-readable reference , while the database keeps a separate immutable internal payment ID. 2. I RECOMMEND THIS STRUCTURE GRAND STORE TRANSACTION REFERENCE GS-[YEAR]-[MODULE]-[TYPE]-[SEQUENCE] For example: Activity Reference Normal product sale GS-26-SHP-SAL-000001 Auction GS-26-AUC-BID-000002 Auction payment GS-26-AUC-PAY-000002 Event booking GS-26-EVT-BKG-000003 Vendor registration GS-26-VND-REG-000004 Vendor monthly fee GS-26-VND-SUB-000005 Vendor commission GS-26-VND-COM-000006 International wine purchase GS-26-GLO-SAL-000007 Wine estate experience GS-26-EST-BKG-000008 Refund GS-26-RFD-000009 Shipping GS-26-SHP-DEL-000010 The key is that  AUC can never be confused with EVT , and  EVT can never be confused with a normal product sale . 3. BUT DON'T PUT EVERYTHING INTO ONE REFERENCE This is important for the developer. You should have several linked IDs. For example, an auction customer pays R52,500. The system could have: Customer CUS-000457 Auction AUC-000027 Lot LOT-000184 Order ORD-000921 Payment PAY-001284 Invoice INV-001102 Transaction GS-26-AUC-PAY-001284 All of these are linked in the database. So  your accountant can search  any one of them  and reach the entire transaction history. 4. CREATE A "MODULE CODE" SYSTEM I would establish fixed codes that  never change .
